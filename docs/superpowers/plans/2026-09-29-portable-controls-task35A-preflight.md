## What this test must prove

One test, one shipping path, from the IDE command to a running label:

1. the generated **Add Web Form (portable)** command creates the document + code-behind in a real
   temp web project;
2. Label, TextBox and Button arrive through the real canvas drop path at two window sizes;
3. a real double-click on the Button writes the portable handler stub **after** the init region;
4. the handler body is written through the real code editor and saved with `SaveAsync`;
5. the generated project builds to a web site through both `BuildService` and the CLI, and Edge
   types, clicks and reads the Label;
6. the same document is retargeted with `FormRetarget.ConvertToPair`, built through the CLI + csc,
   and the WinForms reference window gets the same input and reads the same Label.

Any absence of Edge, Node, dotnet, or the Windows Desktop SDK must make the test **skip**, never
pass. `PortableRuntimeHarnesses.RequireWeb()` is the first statement.

## Decisions

**Construct the real `MainWindowViewModel` through the container.** It has ~40 constructor
dependencies and no test constructs it directly. The test uses
`ServiceConfiguration.ConfigureServices()`, overrides only `IDialogService` (the form-name prompt),
opens the temp project with the real `IProjectService`, then resolves `MainWindowViewModel` from the
same provider. The real `IFileService`, `IProjectService`, `BuildService`, event aggregator and
`DockFactory` are used. This is the only practical way to drive the generated command and the
`FileOpenRequested` → open-document route without a hand-built scaffold.

**Retrieve the real documents from the singleton `DockFactory`, not from reflection.** The test
polls `DockFactory.GetAllDocuments()` for the form document and then the code-behind document whose
`FilePath` the command produced. The code document only appears because `MainWindowViewModel`
answered the `NavigateToFileEvent`; that is the shipping route under test.

**Let the project list its sources explicitly.** The temp `.blproj` lists `Main.bas` as a
`<Compile>` item. That keeps `ProjectGlobSafety.MaterialiseGlobbedSources` from firing the
"Project sources listed explicitly" dialog and makes the subsequent `.blwebform` item part of the
explicit build list.

**Use the document's default IDs (`Label1`, `TextBox1`, `Button1`).** They are generated by the real
drop path in a fixed order, so they are stable for the run and keep the handler body deterministic.
The test uses the actual generated `Button1_Click` name rather than inventing a fixture id.

**Two sizes on one form.** The form is opened at 800×560 (zoom ≠ 1), the Label is dropped there, then
the window is resized to 1000×700 (zoom ≠ 1 and different) and the TextBox and Button are dropped.
`FormCanvasTransform.Fit` caps at 1.0, so the second size must stay under the cap to exercise a real
scale. This exercises both sizes through the same real canvas and avoids a duplicate form. The final
document is the one built and retargeted.

**The WinForms retarget gets the same handler body deliberately.** `ConvertToPair` produces a
fresh code-behind with blank stubs; that is the correct retarget contract. The test inserts the same
body that was typed in the editor, so the desktop run receives the same input and can be compared
for the same output. A public empty `Cover` method is added because `RunWinForms` calls it after
`Show`; this is the harness's established entry hook, not a product path.

**The web build is proven twice, then run.** `BuildService.BuildProjectAsync` must succeed and write
its JavaScript site to `bin/Debug` (its configured output path); Edge runs that IDE-built site. The
site is then removed and the real CLI build must recreate the page at its own
`bin/Debug/net8.0` path (the CLI always appends the target framework). This proves the CLI route
independently. The Edge output is compared with the WinForms output.

**The shell must keep its navigation subscription.** `EventAggregator` holds handlers weakly, and
`MainWindowViewModel` discarded the `IDisposable` returned by
`Subscribe<NavigateToFileEvent>`. After a GC, a double-click wrote the handler but no tab opened.
The test exposed this; the view model now retains both subscriptions. The fix is on the shipping
route, not a test seam.

## Test shape

`VisualGameStudio.Tests/Shell/PortableFormEndToEndTests.cs`

- `[TestFixture] [Category("Integration")] [NonParallelizable]`.
- One `[AvaloniaTest]` method.
- Start with `PortableRuntimeHarnesses.RequireWeb()`.

- Verify the command's output files and explicit project items before continuing.

- Use `MainEditor.Document.Replace` for the editor edit, then `SaveAsync()`.
- Compare Edge and WinForms output with one expected `"Ada!"`.

## Risks checked by this test

- The command is reachable and opens the document, not just writes files.
- The drop is a real `DragDrop` into the real `FormCanvasControl` at a non-1 zoom, at two sizes.
- Double-click timing uses two real pointer down/up pairs and then polls for the navigated document.
- The handler is not merely in the buffer: the form save regenerates it and the code-behind save
  writes the typed body to disk.
- The web output is from a page emitted by `BuildService`, not from a hand-written fixture.
- The desktop output is from the real CLI + csc path, and its input is delivered as window messages.
