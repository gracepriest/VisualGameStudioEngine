# Phase 0 Spike Results — IL2CPP for VGS

**Date:** 2026-11-01
**Status:** COMPLETE — GO recommendation

## What was done

1. **IL Reader** (`BasicLang/ILReader/ILAssemblyReader.cs`): Uses `System.Reflection.Metadata` to read types, methods, and method body bytes from a .NET PE assembly. Tested on VGS-generated MSIL (`hello.bas --target=msil` → ilasm → .exe).

2. **IL→C++ Emitter** (`BasicLang/ILReader/ILCppEmitter.cs`): Reads the Main method's IL bytes, parses `ldstr`/`call`/`ret` opcodes, resolves user strings via `MetadataReader.GetUserString`, and emits a C++ program using `std::cout`.

3. **Tests** (`VisualGameStudio.Tests/ILReader/`): 2 tests pass — IL reader reads types/methods, emitter produces valid C++.

4. **End-to-end verification:** Emitted C++ compiled with MSVC (`cl /EHsc`) → native `.exe` → ran → printed "Hello, IL2CPP!".

## What worked

- `System.Reflection.Metadata` is built into .NET SDK — no external dependencies.
- Reading types, methods, and method bodies from a PE assembly works reliably.
- Parsing `ldstr` (0x72) + `call` (0x28) + `ret` (0x2A) opcodes is straightforward.
- User strings resolve via `MetadataTokens.UserStringHandle` + `GetUserString`.
- The emitted C++ compiles cleanly with MSVC and runs natively.
- No .NET runtime needed to run the output.

## What was harder than expected

- `ldstr` strings are in the #US (user strings) heap, not the #Strings heap. Required `GetUserString` instead of `GetString`.
- `MetadataTokens.StringHandle` vs `UserStringHandle` distinction — easy to get wrong.
- The IL reader needs a PE assembly, not the `.il` text file. The MSIL backend emits `.il` text; ilasm must assemble it first.

## Estimated effort for Phase 1

- IL reader + type system: ~2 weeks (type definitions, generics, method signatures).
- Method body lowering: ~3 weeks (opcodes, control flow, exceptions).
- Total Phase 1-2: ~5 weeks for basic programs.

## Go/no-go recommendation

**GO.** The spike proves feasibility:
- IL reading works with built-in .NET APIs.
- C++ emission from IL is straightforward.
- Native compilation and execution works.
- No .NET runtime dependency in the output.

The main risk is scope (full IL2CPP is multi-year), but Phase 0 demonstrates the core pipeline works.
